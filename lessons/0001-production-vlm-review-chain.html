Lesson 0001

从 drawio_done 到 VLM Verify

本课的目标：你能看着一次 run，准确指出“谁看图、谁做决定、谁有改图权限，以及为什么不会无限修复”。

1. Draw生成候选 XML
2. Persistversion + hash
3. Review真实 PNG → VLM
4. Decide确定性 policy
5. Repair?最多一次、受限工具
6. Verify只复核，不再修改
7. PresentNDJSON lifecycle
8. Observerun/token/cost

一、VLM 是 Agent，但不是总控 Agent

300018 在配置层确实是一个独立 agent：它拥有独立 prompt、model、temperature=0 和 session。但它没有画布工具。它只把 before/after PNG 与有界文本证据转换成 schema v2 JSON。

核心分权：VLM 负责“看见什么”；Java policy 负责“允许发生什么”；drawer agent 负责“执行什么”。

因此 reviewer 不是可以自由规划的第二个绘图 Agent，而是一个 tool-less perception component。真正编排它的是 CanvasVisualReviewOrchestrator。

二、drawio_done 为什么不是整条链路的 done

绘图模型或工具可能多次产生候选结果。DrawioStreamResponseWriter 先把它们记为 pending candidate，做确定性 XML/geometry 修复，只在流结束时持久化并发送最终候选。此时 drawio_done 表示“这一轮 drawer 已得到一个 canonical canvas”，并不表示视觉审查、可选修复和 verify 都完成。

持久化返回 diagramId + version + contentHash。这三个值是后续 review 的身份证；没有它们，前端不会开始 POST_MUTATION review。

三、为什么必须审真实 PNG

XML analyzer 擅长结构事实：节点数、边、可解析性、几何数据。它不能可靠判断最终像素里的小字、低对比、遮挡或视觉层级。前端等待最终 XML 真正加载进 draw.io iframe，再导出 review PNG。

XML、thumbnail、autosave 和 review PNG 共用一个 iframe export 通道。Coordinator 将请求串行化，并在 export action 中加入 requestId；draw.io 的 response message 会回显原 action，所以迟到回调只能完成自己的 request，不能污染下一张图。官方协议见 draw.io Embed Mode。

四、后端审查的双重 stale 防线

请求带上 expected version/hash。Orchestrator 在调用 provider 前查一次数据库，在 provider 返回后再查一次。任意一次不匹配都返回 STALE，丢弃结果。这样用户在 VLM 思考期间继续编辑时，旧截图不会评价或修改新画布。

五、schema v2 与 decision policy

VLM 最多返回 5 个 issue，每条有 type、severity、可见 anchor、region、evidence、repairInstruction 和结构化 repairScope。解析器要求字段集合完全一致；Markdown、额外字段、未知枚举、过长文本都会变成 UNAVAILABLE(output_schema_error)。

六、自动修复为什么不会越权

Orchestrator 不接受客户端指定的 repair agent，而是固定使用服务器配置的 drawer agent。它把 route 强制成 edit_existing 或 optimize_layout；session allowlist 只允许相应 mutation tool，create_diagram 会在工具执行层被拒绝。skill lookup 不受影响。

修复成功后前端收到新的 drawio_done、保存新 version/hash、重新导出 PNG，并发起 VERIFY_ONLY。Policy 根据 stage 硬性禁止第二轮 repair，因此不会形成 VLM 自我循环。

七、故障和灰度

Fail-open 的准确含义：VLM 不可用时保留已经通过确定性校验并持久化的画布；不是忽略版本冲突，也不是允许不安全修复。

两个开关分别控制 review 和 auto repair。shadow 请求仍调用 VLM并记 telemetry，但不发用户可见 result，也不修图。上线顺序应为 disabled → shadow → visible → auto repair。

八、数据库迁移在链路中的位置

每次模型调用会记录 token，同时用 LlmPricingSnapshot 固化价格表版本、输入/输出单价和估算成本。这样以后价格变化时，历史 run 成本不会被新价格重算。新增列均 nullable，所以迁移后旧记录保持 NULL，新代码开始写快照。本次本地库已有 131 条旧记录，迁移后全部保留。

MySQL 允许一个 ALTER TABLE 中包含多个 ADD COLUMN；本项目通过版本化 SQL 做向前迁移。参见 MySQL 8.4 ALTER TABLE。

检索练习

谁有权把 VLM issue 变成 REPAIR？

CanvasVisualReviewPolicy，不是 VLM。VLM 只返回结构化 evidence。

用户在 VLM 返回前改了图，会发生什么？

第二次 version/hash 检查失败，结果标记 STALE，不展示为当前图结论，也不触发修复。

为什么 verify 不能再修一次？

Policy 要求 stage 必须是首次 POST_MUTATION；VERIFY_ONLY 无论发现什么都不会返回 REPAIR。
