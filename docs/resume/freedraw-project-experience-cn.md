## 推荐版本

### FreeDraw｜AI 原生图表生成与编辑平台（已部署）

**角色：** 全栈开发<br>
**时间：** 2026.05 – 至今<br>
**技术栈：** Java、Spring Boot、Spring AI、Google Agent Development Kit（ADK）、React、MySQL、Pinecone、Docker、AWS、CI/CD

从 0 到 1 构建并部署基于 LLM Agent 的智能绘图平台，支持通过自然语言创建、编辑、还原和审查可编辑的 Draw.io 图表。

- 设计意图路由与分层 Agent 执行架构，隔离普通绘图、画布编辑与资料检索链路；使用结构化 Tool Calling 和 Schema 校验驱动图表生成、审查及修复，降低不同能力之间的耦合。

- 设计分层 Context Engineering 机制，统一管理会话历史、摘要、可信画布快照、本轮附件和 RAG 证据，并根据任务路由按需组装上下文；明确长期 Memory 仅用于用户偏好、不作为事实证据，保障多轮绘图连续性并降低上下文污染。

- 构建面向 PDF 与图片的多模态 RAG 管道，结合语义检索与关键词检索生成资料快照，并将图表元素关联至页级、区域级证据，实现可追溯的资料辅助绘图。

- 设计可靠的图表执行与更新机制，通过请求幂等、原子 Turn Claim、画布版本校验及安全提交，避免并发重试导致的重复执行、旧状态覆盖和错误画布更新。

- 建立“结构校验—视觉审查—自动修复”质量闭环，结合确定性图校验与 VLM 渲染审查，识别并修复节点、连线及布局问题。

- 搭建 Agent 全链路 Trace 与自动化评测框架，结合规则评分和 LLM/VLM Judge，支持失败归因、回归测试及 Agent 迭代优化。

- 使用 React 集成 Draw.io 编辑器与流式 Agent 交互界面，实现附件预览、执行过程展示、对话恢复及图表版本持久化，并通过 Docker、AWS 和 CI/CD 完成应用部署。

## 面试表述边界

- “已部署”需要能够说明部署环境、发布流程、日志监控和故障处理方式。
- “Context Engineering”需要能够说明会话历史、摘要、画布、附件和 RAG 证据如何分层、裁剪并按需注入。
- 只有实现跨会话持久化的用户偏好或长期事实后，才能将其表述为“长期 Memory”；会话记录和摘要本身不等于长期记忆。
- Memory 应保持为个性化偏好来源，不应被表述为资料证据或事实依据。
- “多模态 RAG”需要能够说明附件解析、索引、召回、资料快照和引用生成的完整链路。
- “原子 Turn Claim”需要能够解释幂等键、并发重试、执行所有权及最终提交规则。
- “VLM 视觉审查”需要能够区分确定性结构校验与视觉模型审查各自负责的问题。
- “自动化评测”需要能够说明测试样本来源、评分方式、Trace 关联和回归门禁。
- 如果某项能力仍在开发或尚未稳定上线，应使用“设计并实现”或“搭建”，避免写成已经产生生产收益。
